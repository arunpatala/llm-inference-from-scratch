# Writing-style system: avoiding LLM-sounding prose

## Problem statement
Core concern for this project: readers now instantly recognize and discount
LLM-generated prose. Since this book is LLM-assisted by design, this had to
be solved structurally, not left to vibes. User's proposed mechanism:
interview the user with questions per chapter, and build the chapter from
their actual answers rather than restated general knowledge.

## Research — what to avoid
- [Wikipedia: Signs of AI writing](https://en.wikipedia.org/wiki/Wikipedia:Signs_of_AI_writing) —
  the canonical, actively-maintained source (Wikipedia editors fight this at
  scale). Categorizes content/language/style/formatting/citation tells.
  Core caveat used throughout: signs are only meaningful when they **cluster**
  — a single instance of "crucial" proves nothing.
- Existing Claude Skills doing this already: `blader/humanizer` (built
  directly from the Wikipedia guide, 33-pattern framework), `lguz/humanize-writing-skill`,
  `celestialdust/humanize-prose`, `conorbronsdon/avoid-ai-writing`.
- [arXiv 2603.27006, "The Last Fingerprint"](https://arxiv.org/html/2603.27006v1) —
  the most non-obvious finding: markdown-heavy training data causes LLMs to
  default to "structured document" mode even when flowing prose is wanted
  (unsolicited headers, bullet-ifying flowing thought, bold-everything,
  reflexive colon-then-list, elevated em-dash rate as the "smallest
  surviving unit" of this tic). Directly relevant since this whole book is
  markdown.

## Research — what to do instead (positive craft, added after user pushback
that a banned-word list only says what not to write)
- [Diátaxis](https://diataxis.fr/) — the documentation framework behind
  Stripe's/Django's/Python's docs. Four modes (tutorial/how-to/
  reference/explanation) that should not be mixed within one piece of
  writing; muddiness from mixing modes reads as generic more than any single
  word choice does.
- [Google developer documentation style guide](https://developers.google.com/style) —
  second person, active voice, present tense, "a knowledgeable friend" tone.
- [Worked-example effect](https://en.wikipedia.org/wiki/Worked-example_effect) /
  cognitive load theory — show one fully-solved concrete instance before
  asking the reader to attempt the general case; matches the hybrid exercise
  style already chosen for the course.
- ["100 things I learned writing my first technical book"](https://dev.to/viebel/100-things-i-learned-writing-my-first-technical-book-2np3) —
  concrete-to-abstract ordering, one objective per chapter, motivate before
  mechanism, real values in examples (not `foo`/`bar`), verify every code
  snippet actually runs, write the chapter intro last.

## What was built
Project-scoped Claude Skill at `.claude/skills/write-chapter/` (auto-loads
for any prose work in this project):

- **`SKILL.md`** — the workflow. Interview-first (6 fixed questions asked
  before any chapter is drafted; chapter is written *from* the answers, not
  general knowledge; thin answers get a follow-up, not a generic fill-in).
  Hard factual rule: every number/claim must trace to this project's own
  test/benchmark output or a real citation — never fabricate a plausible
  number. Done-checklist: confirm one clear mode/objective, run the linter,
  read-aloud check, re-check both reference files (they grow over time).
- **`references/style_rules.md`** — the "what to avoid" list. ~60 banned
  words/phrases with plain-English replacements (seeded from the Wikipedia
  guide), banned structural patterns (negative parallelism, rule of three,
  formulaic concession-conclusions, copula avoidance, vague attribution,
  hedging stacks, chatbot formalities), markdown-formatting discipline
  (headers/bullets/bold/em-dash), and a counterindicators section (don't
  over-correct on isolated non-clustered instances). Has a changelog for
  future additions.
- **`references/craft.md`** — the "how to write" positive counterpart. Pick
  one Diátaxis mode per chapter; concrete-before-abstract; worked example
  before the reader's own attempt; motivate before mechanism; voice rules;
  per-chapter structural discipline; revise-in-this-order (hook written
  last). Has its own changelog.
- **`scripts/style_lint.py`** — parses the banned-word list directly out of
  `style_rules.md` (single source of truth, can't drift out of sync).
  Flags case-insensitive whole-word-plus-inflection matches with line
  numbers, negative-parallelism regex, and structural stats (bullet-line
  ratio, heading-to-paragraph ratio, bold density/1000w, em-dash
  density/1000w) with WARN thresholds.

## Verification
Smoke-tested against a deliberately bad sample (caught 7 banned words
including inflected "leverages", the negative-parallelism pattern, and 2
structural warnings — header-per-paragraph ratio and em-dash density; exit
code 1) and a clean human-voiced sample (zero hits, zero warnings; exit code
0). Suffix-matching bug (missed inflected forms like "leverages") found and
fixed during testing.

## Status
Fully built and tested, not yet applied to any real chapter (none written
yet). User will hand over additional smells/techniques over time — just
append to the relevant changelog and section in `style_rules.md` or
`craft.md`, no code changes needed for word-list additions.
